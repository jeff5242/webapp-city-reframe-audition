## 1. 地政網站資料擷取：同意方向，但「爬網站」要改成「接官方圖資」

### 先分清楚兩類資料，法律待遇完全不同

| 類別 | 內容 | 可否自動取得 |
|---|---|---|
| **公開圖資** | 地號範圍／坐標、面積、使用分區、公告現值、都市計畫圖層 | ✅ 有官方服務可接，且多為開放資料 |
| **謄本類** | 所有權人姓名、身分證、住址、他項權利 | ❌ **不可自動抓**——第一/二類謄本需權利人或代理人身分調閱，內含個資 |

第二類必須由實施者依法定程序調閱（通常委託代書），系統只能接
「**上傳謄本檔 → 解析**」，不能代為登入抓取。這點如果沒講清楚就做下去，
會同時踩到個資法與各系統的使用條款。

### 建議做法

- **公開圖資**：以官方服務帶入「地號 → 範圍／面積／分區／公告現值」，
  自動填入基地位置與範圍。候選來源（**需逐一查證可用性與授權條款**，
  我不憑印象下結論）：國土測繪中心地籍圖資服務、TGOS 圖資服務平台、
  各縣市都市計畫查詢服務、政府資料開放平台的地價與分區資料集。
  → **建議先做一次技術探查**：確認有無穩定 API、授權是否允許商業使用、
  有無流量限制，再決定接哪幾個。
- **謄本類**：走「上傳 → 解析」。這裡有個現成優勢——
  **協檢端的地端 VLM（Qwen2.5-VL）本來就在做密集表格抽取**，
  謄本結構比審議資料表更規則，準確率應該更好。
  而且**謄本含個資必須地端處理**，正好坐實我們地端架構的價值。

### 要避免的陷阱

自動帶入的資料**不可直接當定稿**。建議一律標示「系統帶入（來源：○○，擷取日 ○○）」，
並要求承辦確認——地籍資料會變動，帶入當下正確不等於報核時正確。
這點也符合我們「AI 只遞素材、人做確認」的一貫定位。

## 2. 原始文件匯入與圖文解析：最大的槓桿不在 OCR

### 可行度分級（誠實版）

| 文件 | 可行度 | 說明 |
|---|---|---|
| 謄本（PDF 有文字層） | **極高** | 直接讀文字，不用 OCR |
| 謄本（掃描件） | 高 | 沿用協檢端 VLM |
| 地籍圖地號標註 | 高 | VLM 辨識 |
| 信託／合約條款抽取 | 中 | LLM 可抽，**必須人工覆核**（金額與期限錯不得） |
| 從建築圖「抓取文字與尺寸」 | **不建議走 OCR** | 見下 |

### 這裡有個免費的巨大槓桿：要原生檔，不要掃描件

建築師手上本來就有 **DWG**，代書手上本來就有**電子謄本 PDF**。
從 DWG 直接讀圖層、尺寸標註、地號，準確率是 **100%**；
把同一張圖印成 PDF 再 OCR，準確率大概 90% 上下，而且錯在哪你不知道。

**建議把「原生格式優先」寫進收件規格**：DWG／電子謄本 PDF／Excel 為第一順位，
掃描件是 fallback。這件事不花一毛錢開發費，效果比再強的 OCR 都大。
反過來說，如果副幹事長的痛點正是「上游只肯給掃描件」，
那要解的是**流程與合約條款**，技術只能補到八九成。

## 3. 條件式選項與法規模組化：建議第一個做

### 為什麼這項優先

副幹事長講的「四選一」，正是文件自動化產品的核心機制（條件式段落）。
對我們特別划算的三個理由：

1. **架構同構**：現有 `NarrativeSection` 已經有「寫作要點＋適用法源＋章節輪廓」，
   只要加一層「情境」維度就成立，不用重寫。
2. **修掉現有弱點**：目前敘述素材是自由文字，品質全看承辦寫什麼。
   改成「選情境＋填條件」，輸出穩定度大幅提升。
3. **更符合誠實邊界**：**法條是選出來的，不是 AI 想出來的**。
   這比讓 AI 自由引法源更安全，也更好跟委員解釋。

### 實作構想

```
ScenarioProfile（情境）
  ├─ 觸發條件（屋齡、面積、是否公劃更新地區、是否危老合併…）
  ├─ 對應法條（固定清單，不由 AI 決定）
  ├─ 敘述骨架（段落結構與必提要素）
  └─ 需補欄位（該情境特有的資料）
```

使用者選情境＋填條件 → 系統帶入法條與骨架 → AI 只負責把素材寫成通順文字。

### 重要：情境不要拍腦袋想，要從實案歸納

建議請副幹事長提供 **5–10 本過去的計畫書**（或先從芝山段這本開始），
把「計畫緣起」「辦理緣起」段落做分類，歸納出**真實存在**的情境有哪幾種。
拍腦袋設計的四選一，第一次遇到真案就會發現少一種。

## 4. 客製化排版與圖紙輸出：抽成 Profile，但有三處要先問清楚

### 好消息：剛做完的東西正好對上

A3 橫式輸出、比例尺受控計算、2-up 併頁——上週才完成，而且是**硬編在常數裡**
（`FIGURE_PAGE="A3"`、留白 15mm、比例尺政策）。
建議抽成 **`LayoutProfile`**（每客戶／每案一組），隨 bundle 走：

輸出紙張、留白、2-up 規則、圖框樣式、比例尺政策（是否強制標準比例）、
頁碼格式（分章「9-12」式或流水號）、封面樣式。

這是低風險重構，做完就等於「系統記得這家客戶的排版習慣」。

### 三處要向副幹事長確認（我不猜）

1. **「兩張當作三頁排列」**是什麼？可能是 A3 圖攤開跨兩頁對開、
   或三頁一組的摺頁、或 2-up 中某些頁單獨——**三種做法完全不同**，
   請他畫個示意或指一本既有的書給我們看。
2. **「圖紙的重疊方式」**是指圖層疊合（地籍圖疊都市計畫疊建築配置），
   還是排版上的圖面重疊？前者屬 GIS 製圖、後者屬版面，處理方式不同。
3. **比例尺規範**：是否要求一定落在標準值（1/200、1/300…）？
   若是，上游出圖時就要用「預備縮製」的比例反推
   （例：知道要縮 2.33 倍，就以 1/700 反推出圖）——這要跟建築師講清楚。

## 5. 漸進式生成與「陪跑」定位

### 5a 漸進式生成：能力已有，缺的是引導

「給大方向 → 先出前期資料 → 逐步補」——這些能力我們都有
（章節可各自生成、缺件清單、章節狀態機），但介面沒有「引導感」。

建議加一個**生成進度視圖**：哪些章現在就能生成、哪些卡在缺什麼資料、
補齊哪一項可以解鎖哪幾章。把現有的缺件清單從「清單」升級成「路徑圖」。

### 5b ⚠️ 「生成審查意見」——這項我必須擋一下

**問題**：我們對市府與理事長的定位是「收件端前處理、AI 只標示疑義、
不做肯定性結論」，並且明講「**協檢不協審**」。
如果生成端產品宣稱「自動生成審查意見」，同一家公司等於一邊說
「AI 不做審查判斷」，一邊賣「AI 幫你寫審查意見」——
被委員或媒體問到會很難答，而且會回頭傷害市府端的信任。

**但客戶的真實需求是合理的**：他想先知道「這本書送出去會被問什麼」。

**建議改寫成「送件前預審自檢報告」**：

- 內容＝用**我們自己的協檢引擎**跑過這本書，列出規則命中的疑義
  ＋歷史上常見的退補件原因。
- 定位＝「**用同一把尺自我檢查**」，不是「模擬委員審查」。
- 話術＝「送件前自檢」，不用「審查意見」「模擬審查」這類詞。

這樣既滿足需求，又**正好落地我們提案書寫的「生成×協檢閉環」差異點**——
從賣點變成看得見的功能。

### 「協調結果」也要分清楚

若指所有權人協調會議的**結論**（誰同意、誰不同意），
那是事實記錄，AI 編造有法律風險，**不做**。
可以做的是**協調進度追蹤與統計**（同意比率即時計算——這個我們已經有了）。

## 建議排程

| 批次 | 內容 | 前提 |
|---|---|---|
| **A（可立即）** | 條件式情境選單（先做「計畫緣起」一章打樣） | 請副幹事長給 5–10 本舊案供歸納 |
| **B** | LayoutProfile 抽離＋排版偏好儲存 | 先澄清上述三個排版問題 |
| **C** | 送件前預審自檢報告（接協檢引擎） | 先與理事長／市府端確認話術定位 |
| **D** | 官方圖資帶入（地號→範圍/分區/現值） | 先做 API 可用性與授權查證 |
| **E** | 謄本／地籍圖解析（沿用協檢 VLM） | 先立「原生格式優先」收件規格 |
| **F** | 生成進度視圖（漸進式生成引導） | 無 |

## 要跟副幹事長回問的清單

1. 「兩張當作三頁排列」請給示意或既有書為例。
2. 「圖紙重疊」是圖層疊合還是版面重疊？
3. 比例尺是否要求落在標準值？
4. 「審查意見」他期待的是「預想會被問什麼」，還是「代寫審議會意見紀錄」？
   （前者可做，後者不做）
5. 能否提供 5–10 本舊案，供情境歸納與篇幅基準？
   （需書面同意作為系統參考素材——這件事建議一併寫進合作契約）
