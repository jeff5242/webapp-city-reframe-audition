# 都更計畫書 AI 生成系統 — 開發規格書

版本：v0.1（2026-09-14）｜作者：MilkIdea 技術團隊
狀態：草案，供內部開發與華電/學會技術對齊用

---

## 1. 系統概觀

### 1.1 目標

讓原本在 Word 上人工撰寫事業計畫書的人，改為「把資料交給系統，由系統先生成」：

- 產出 200+ 頁、符合 111 年公版（18 章＋附錄）的事業計畫書（第三期擴及權利變換計畫書）。
- 全書數字由單一資料源渲染，前後一致是結構保證。
- 交件前以協檢引擎（收件端前處理系統同一套規則）自檢，附檢核報告。
- 個資（PII）自生成起即被標記追蹤，支援個資索引表與（第三期）公開遮蔽版。

### 1.2 與既有協檢系統的關係

| 系統 | 角色 | 部署 |
|---|---|---|
| 協檢系統（本 repo，既有） | 收件端前處理：規則引擎、法規 wiki、審議資料表抽取 | 雲端（既有 EC2） |
| 生成系統（本規格書，新建） | 撰寫端：資料收集、文件生成、自檢、備份 | 地端 App ＋ 生成雲服務 |

生成雲**不重寫**協檢邏輯，透過 API 呼叫既有協檢服務；法規 wiki 年版資料為兩系統共用。

### 1.3 核心設計原則

1. **單一資料源**：所有數字、姓名、地號只存在於 project bundle，文件是渲染結果。
2. **確定性優先**：表格/計算/公版條文為確定性渲染；LLM 只寫敘述段，且每段附法源引用。
3. **地端可離線**：無網路時可完成資料輸入、彙整、確定性章節生成與預覽。
4. **PII 是 schema 屬性**：欄位定義時即標記 `pii`，非事後掃描。
5. **AI 產出＝草案代擬**：專業人員覆核簽證後定稿，系統保留覆核紀錄。

## 3. 資料模型（core schema）

### 3.1 project bundle

```
project_bundle.zip
├── manifest.json        # bundle 版本、sha256 清單、schema 版本、產生時間
├── project.json         # 主資料（見 3.2）
├── attachments/         # 地籍圖、規劃圖、會議紀錄 PDF、謄本
├── generated/           # 已生成章節 DOCX/PDF（含版次）
└── review_log.jsonl     # 章節狀態機事件（誰、何時、草稿→確認→鎖定）
```

### 3.2 project.json 主要區塊（pydantic v2 定義，輸出 JSON Schema）

| 區塊 | 內容 | PII |
|---|---|---|
| `case_info` | 案名、更新單元範圍、行政區、實施者、報核目標年版 | 部分 |
| `land_parcels[]` | 地號、面積、使用分區 | — |
| `buildings[]` | 建號、樓層、面積 | — |
| `owners[]` | 姓名、身分證、住址、持分（分子/分母）、同意狀態 | **✅ 全欄位** |
| `meetings[]` | 會議類型（公聽會/說明會）、日期、紀錄檔 ref、決議摘要 | 部分 |
| `far_bonus` | 容積獎勵項目、申請值、法源條次 | — |
| `finance` | 成本、共同負擔、估價基準 | — |
| `figures[]` | 圖檔 ref、圖名、比例尺、對應章節 | — |
| `narrative_inputs` | 各敘述章的素材要點（人工填或會議紀錄萃取） | — |

**PII 規格**：每個欄位在 pydantic model 以 `Field(json_schema_extra={"pii": "name|nid|addr|share"})` 標記。渲染器輸出任何 PII 值時，同步寫入 `pii_manifest.json`（值的雜湊、類型、章節、頁碼、bbox）——這是個資索引表與遮蔽版的資料來源，**第一天就要進 schema，事後補標會重工**。

### 3.3 驗證規則（匯入時即跑，fail fast）

- 持分：同一地號所有權人持分加總 = 1（分數運算，不用浮點）。
- 身分證/統編檢核碼、地號格式（段小段-母號-子號）、日期民國/西元正規化。
- 清冊 vs 地籍圖檔案數對應；缺件清單 = 公版必附文件對照表（複用協檢 DOC 規則清單反向使用）。

## 4. 地端程式規格

### 4.1 技術選型

| 項目 | 選型 | 理由 |
|---|---|---|
| 語言/框架 | Python 3.12 + FastAPI（本機 `127.0.0.1:port`） | 團隊既有能力；與雲端/協檢同棧，core 套件直接共用 |
| UI | Jinja2 + HTMX ＋少量原生 JS | 無前端 build chain；表單/精靈型 UI 足夠；與協檢 webapp 模板經驗一致 |
| 桌面外殼 | pywebview（開機自啟本機服務＋內嵌視窗） | 比 Electron 輕百倍；不想裝也可純瀏覽器開 |
| 打包 | PyInstaller one-dir，Windows 優先（客戶端多為 Win） | 單資料夾免安裝；更新 = 換資料夾 |
| 本機儲存 | SQLite（WAL）＋ Vault 目錄（附件原檔） | 零維運；bundle 匯出直接打包 |
| DOCX 渲染 | docxtpl（python-docx-template）＋公版 Word 母版 | 客戶可拿 DOCX 回 Word 改；母版一次做好格式全書一致 |
| 本機 PDF 預覽 | 章節 HTML 預覽為主；偵測到本機 LibreOffice/Word 時提供整書 PDF | 不把 300MB LibreOffice 塞進安裝包 |

### 4.2 功能清單（依畫面）

1. **案件列表**：建案、開啟、匯出 bundle、同步狀態（未上傳/已上傳/雲端已回）。
2. **收件精靈**：分區表單（case_info → 清冊上傳 → 會議 → 獎勵 → 圖檔），每步即時驗證，隨時顯示**缺件清單**。
3. **清冊匯入**：提供官方 Excel 範本下載；上傳後逐列驗證，錯誤列標紅可下載修正版。
4. **章節工作台**：18 章樹狀清單，每章顯示類型（確定性/敘述/附錄）與狀態（待資料/已生成/覆核中/鎖定）；確定性章一鍵生成、HTML 預覽、DOCX 下載。
5. **敘述章**：離線時顯示佔位與素材填寫區；雲端回包後顯示 AI 草稿＋法源引用，覆核者可改後標記確認。
6. **自檢面板**：本機協檢-lite 結果（缺件、一致性、獎勵上限）；雲端完整自檢報告回傳後在此對照顯示。
7. **同步**：一鍵打包上傳；離線時進佇列，連網自動補送；顯示雲端法規年版警示（例：報核年版對應之法規已更新）。

### 4.3 地端協檢-lite

從 core 套件引入純 Python 規則子集（不含 OCR/LLM）：缺件對照、清冊一致性、容積獎勵 ≤ 上限、日期邏輯。規則快照隨 App 版本發布，UI 明示「以雲端複驗為準」。

## 5. 生成雲服務規格

### 5.1 技術選型

| 項目 | 選型 |
|---|---|
| 服務 | FastAPI（新服務 `renewal-gen-cloud`，獨立於協檢 webapp 部署） |
| 儲存 | S3（bundle 與產出物，SSE-AES256、版本化）＋ PostgreSQL（案件索引、任務狀態）；POC 期可先 SQLite |
| 任務佇列 | 先同步 API＋背景 task（FastAPI BackgroundTasks）；量大再上 Redis/RQ |
| PDF 組版 | LibreOffice headless（容器內建）；目錄/頁碼由 Word 域更新後轉出 |
| LLM | Anthropic Claude：敘述章生成 `claude-sonnet-5`；素材萃取（會議紀錄→決議摘要）`claude-haiku-4-5`；設計成 env 可換模型（同協檢系統慣例） |
| 協檢整合 | HTTP 呼叫既有協檢服務 `/audit`（自檢版）；法規年版資料以 wiki repo 為單一來源 |

### 5.2 API（v1）

| Endpoint | 功能 |
|---|---|
| `POST /v1/bundles` | 上傳 bundle（presigned S3 直傳＋回呼登記）；驗 manifest sha256 |
| `POST /v1/bundles/{id}/generate` | 觸發：敘述章生成（指定章或全部）＋會議紀錄素材萃取 |
| `POST /v1/bundles/{id}/validate` | 完整複驗：確定性章節重渲染比對＋協檢引擎自檢＋法規年版檢查 → 自檢報告 |
| `GET  /v1/bundles/{id}/result` | 結果包下載（敘述章草稿、自檢報告 HTML/JSON、年版警示） |
| `POST /v1/bundles/{id}/assemble` | 全書組版：合併章節 → 目錄頁碼 → PDF＋DOCX＋pii_manifest |
| `GET  /v1/regulations/current` | 目前法規年版與生效日（地端啟動時比對快照新鮮度） |

認證：POC 期 per-客戶 API key（`Authorization: Bearer`）；商業化改帳號/租戶。

### 5.3 複驗（validate）的定義

1. **重渲染比對**：雲端用同版 core 重新渲染確定性章節，與地端上傳的產出逐一 diff——抓地端版本過舊或人工改壞數字。
2. **協檢自檢**：組版後 PDF 丟協檢引擎，產出與收件端同格式的檢核報告（形式齊備、數字勾稽、獎勵上限、用詞）。
3. **法規年版檢查**：依報核目標日期選版（沿用協檢 version_selector 邏輯），比對 bundle 引用的法源條次是否屬該年版，列出已修正條文警示。

### 5.4 LLM 敘述章生成規格

- 輸入：該章 `narrative_inputs` 素材＋case_info 摘要＋該章公版寫作要點＋適用年版法源條文（從 wiki 取，帶條次）。
- 輸出格式：`tool_use` 強制 JSON——`{paragraphs: [{text, citations: [{law, article, year}]}]}`，無引用之法規陳述一律拒收重生。
- 防幻覺鐵律（沿用 PDF 抽取經驗）：prompt 明令**不得推算、不得補全未提供的數字**；文中數字只能來自 schema 欄位佔位符（渲染期代入），LLM 產文用 `{{far_bonus.total}}` 這類 token 而非直接寫數字。
- 敘述章草稿一律標記 `draft`，覆核者在地端確認後才進組版。

## 6. 同步協定

- **格式**：`project_bundle.zip`，manifest 含 schema 版本、每檔 sha256、上傳者、時間。
- **傳輸**：TLS；大檔走 presigned S3 分段上傳；離線佇列存本機，連網 FIFO 補送。
- **版本**：bundle 每上傳一次一個 immutable 版本（S3 versioning）；雲端保留全歷史 = 備份需求。
- **衝突**：單機編輯為主（POC 假設一案一機）；上傳時若雲端有更新版本，回 409 附 diff 摘要，由使用者決定覆蓋或拉回——不做自動合併。
- **回傳**：結果包同樣 zip＋manifest，地端匯入時驗 sha256、按章節合併（僅覆蓋 `draft` 狀態章節，`鎖定`章節絕不覆蓋）。

## 7. Monorepo 與開發方式

```
renewal-suite/
├── core/                 # pydantic schema、驗證器、docxtpl 渲染器、協檢-lite 規則、bundle 打包
│   └── tests/            # 單元測試（TDD，80%+）
├── desktop/              # 地端 App（FastAPI+HTMX+pywebview+打包腳本）
├── cloud/                # 生成雲服務
├── templates/            # 公版 Word 母版、章節模板、清冊 Excel 範本
│   └── gold/             # 示範案例 gold bundle（去識別化）——驗收腳本的基準
└── scripts/acceptance.py # 驗收清單腳本（3.4 驗收標準自動化）
```

- **core 是唯一真理**：地端與雲端都只依賴 core，禁止兩邊各寫一份渲染/驗證邏輯。
- **開發流程**：TDD（先寫測試）；每章渲染器附 snapshot 測試（DOCX 解包比對關鍵 XML）；conventional commits；PII 樣本資料絕不進 git（沿用協檢 repo 鐵律，gold bundle 一律去識別化）。
- **驗收腳本**：`acceptance.py` 對任一 bundle 跑：章節完整率、內部一致性 0 錯誤、協檢-lite 通過、敘述章引用齊備——每輪 demo 附報告，也是 CI 迴歸測試。

## 9. 安全與個資

1. 地端資料不離開客戶機器，除非使用者明示上傳；上傳範圍在 UI 逐項列出。
2. S3 全程 SSE-AES256＋bucket 私有；bundle 下載一律 presigned 短時效 URL。
3. 雲端日誌去識別化（記欄位路徑不記值）；LLM prompt 中的 owners 個資僅在敘述章確需時傳入，且優先以佔位符替代實值。
4. gold/測試資料一律去識別化；`.gitignore` 涵蓋 bundle 與附件目錄。
5. API key 洩漏處置：金鑰輪替端點＋撤銷清單。
